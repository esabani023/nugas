Tahapan desain sistem merupakan jembatan untuk menjawab "bagaimana" sistem akan dibangun berdasarkan rumusan "apa" yang telah dikumpulkan pada fase analisis (RDD, DFD, dan Diagram UML pada tugas-tugas sebelumnya). Berikut adalah analisis komprehensif mengenai kelanjutan Sistem Informasi Perpustakaan Universitas XYZ ke tahap desain:

  1. Pemodelan Data Utama (ERD dan Diagram Relasi Fisik)
    Berdasarkan class diagram pada tugas 3, entitas logis ditransformasikan menjadi rancangan fisik berupa 15 relasi/tabel basis data. Keputusan desain utamanya meliputi:
    • Rantai Transaksional Inti: Dipetakan secara ketat melalui relasi Buku → EksemplarBuku → DetailPeminjaman → Peminjaman → Pengembalian → Denda.
    • Hierarki Pengguna (Supertype/Subtype): Entitas User dirancang sebagai supertype yang memegang data autentikasi sentral (id, username, password_hash, role), yang kemudian diturunkan ke 5 subtype: Anggota, Pustakawan, Kepala Perpustakaan, Pimpinan Universitas, dan Admin Sistem.
    • Penanganan Atribut Turunan: Untuk menjaga akurasi real-time (seperti jumlah eksemplar tersedia atau hari keterlambatan), atribut turunan tidak disimpan secara fisik di tabel, melainkan dihitung langsung melalui query (komputasi dinamis). Hal ini menjawab akar masalah dari pencatatan Excel sebelumnya yang sering tidak sinkron.
    • Log Audit: Penambahan tabel LogAktivitas untuk mencatat jejak rekam sistem (akuntabilitas keamanan).
  2. Strategi Akuisisi Sistem (Make vs. Buy)
    Berdasarkan batasan RDD (waktu hanya 4-6 bulan dan Tim IT kampus lebih berpengalaman di web profil daripada sistem transaksional), maka strategi akuisisi disusun berdasarkan prioritas berikut:
    • Prioritas 1: Aplikasi Paket Siap Pakai (COTS - Commercial Off-The-Shelf). Karena domain perpustakaan memiliki standar proses yang baku (sirkulasi, denda, katalog), menggunakan perangkat lunak paket adalah yang tercepat. Sistem ini harus melalui fit-gap analysis selama 3 minggu terhadap skenario RDD kita.
    • Prioritas 2: Outsourcing (Vendor). Jika aplikasi paket tidak memenuhi kebutuhan esensial tanpa modifikasi source code, langkah selanjutnya adalah menyewa vendor. Kontrak wajib memuat klausul kepemilikan source code, kerahasiaan data anggota, dan transfer wawasan (knowledge transfer) ke Tim IT kampus.
    • Tidak Direkomendasikan: Kustomisasi In-House. Membangun sendiri dari nol oleh Tim IT internal berisiko tinggi memundurkan jadwal proyek dan menurunkan kualitas kelayakan sistem.
  3. Rancangan Arsitektur Sistem Berbasis Web
    Arsitektur yang direkomendasikan adalah Client-Server 3-Tier dengan antarmuka Thin Client (dijalankan murni via web browser). Pembagiannya adalah:
    • Tier Presentasi (Client): Berada di browser pengguna. Dirancang responsif agar anggota dapat mengakses katalog online dari smartphone/gawai dengan mulus (memenuhi UR-02).
    • Tier Aplikasi (Web Server): Mengelola logika bisnis utama (validasi ketersediaan buku, algoritma perhitungan denda otomatis, dan pembuatan laporan).
    • Tier Data (Database Server): Menyimpan 15 tabel relasi. Pemisahan logis ini memudahkan sistem untuk di-scale up jika beban harian meningkat.
    Sebagai catatan, arsitektur harus mengakomodasi Role-Based Access Control (RBAC), hashing password, serta dioptimalkan agar response time saat transaksi peminjaman kurang dari 3 detik untuk menghindari antrean di jam sibuk.
  4. Rancangan Antarmuka (UI/UX)
    Antarmuka tidak hanya sekadar visual, namun merupakan implementasi Boundary Class. Prinsip utama perancangannya adalah:
    • Berbasis Peran (Role-Based UI): Navigasi menu disesuaikan dengan hak akses. Anggota melihat dashboard riwayat pinjam, Pustakawan melihat form sirkulasi, dan Kepala Perpustakaan melihat dashboard pelaporan grafis.
    • Manajemen Kecemasan Pengguna (NFR-01): Karena Pustakawan Senior terbiasa dengan metode manual, alur Form Peminjaman dan Pengembalian dirancang agar mirip secara psikologis dengan urutan kerja buku catatan mereka (content awareness dan tata letak konsisten).
    • Minim Upaya & Pencegahan Kesalahan: Diterapkan aturan maksimal 3 klik dari menu utama. Input kode anggota dan kode eksemplar diintegrasikan dengan alat barcode scanner untuk meminimalisir pengetikan. Setiap tindakan destruktif (seperti menghapus data/akun) wajib memicu kotak dialog konfirmasi.

Kesimpulan

Transisi dari tahap analisis ke desain untuk Universitas XYZ membuktikan bahwa setiap model yang sudah dibuat sebelumnya memiliki fungsi teknis. DFD dan Use Case menjadi acuan pembuatan Antarmuka, Class Diagram bertransformasi menjadi rancangan fisik ERD, dan Sequence Diagram mendikte di mana logika aplikasi ditempatkan pada Arsitektur 3-Tier. Rancangan desain ini kemudian akan berfungsi ganda, yaitu sebagai parameter uji (jika membeli aplikasi paket) atau sebagai blueprint teknis (jika menggunakan jasa vendor).
